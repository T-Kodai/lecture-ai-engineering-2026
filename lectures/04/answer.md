- 気づき・疑問：
  - 直す前の採点では、LLM との不一致は、コードで判定する「回の表示」の 2 件（#05・#07）だけだった（直した後や繰り返しの採点では、#06・#08 の不一致も出た）。コードは末尾の行に「第N回」という文字があるかだけを見るので、「分かりませんでした（第4回）」は合格、範囲外を正しく断った「関係する回：なし」は不合格になる。
    1 つに決まる観点はコードで判定するとよいが、規則が意図とずれることもあり、規則そのものも確かめる必要がある。
    自分でラベルを付けるときも、回の表示は「第N回という文字があるか」と「関係する回を正しく示しているか」のどちらで判断するかで迷い、難しかった。講師と判定が割れた 3 項目のうち 2 つがこの基準だった。
  - #08 の根拠は、講師と自分で割れ、LLM も回によって pass と fail が割れた（直した後は 3 回中 2 回 pass）。「根拠」を「内容が用語集と矛盾しないか」だけで見るか、「出してはいけない場面で出したか」まで含めるかが、基準に書かれていないためだと思う。
  - 一致率は高く見えるが、LLM が判定する 4 基準で自分が不合格にした項目は少ない（根拠 2 件、範囲・ヒント・分かりやすさ各 1 件）。講義の「一致率ではなく、不合格の再現率を見る」のとおり、10 件では不合格の見逃しを測るには足りない。

## 宿題

- 取り組んだレベル：**基礎**（判定の順序：理由を先に書かせる／判定を先に書かせる）
- やったこと：
  - 比べるために [`scripts/judge_order_lec04.py`](../../scripts/judge_order_lec04.py) を作った。採点・集計の関数は `app/judge.py` のものをそのまま使う。`rubric.md` は演習で直した後のもの、ラベルは演習と同じ `labels.jsonl`。
    - 理由が先：`app/judge.py` の採点そのまま（`CriterionVerdict` は reason → verdict の順）
    - 判定が先：順序を述べている 3 か所をすべて逆にした（出力の型のフィールド順、出力形式の指示文、`rubric.md` の「先に理由を書いてから判定を決める」の行）。型の順だけを変えると、残りの 2 か所が「理由が先」と言ったまま矛盾するため。`app/judge.py` 自体は変えず、逆順の型をスクリプトの中で定義した
  - 各 3 回ずつ採点し、一致率・要確認に加えて、モデルの応答で reason と verdict が実際にどちらの順で並んでいたかも記録した（[`results/order/`](results/order/)）。
    保存したのは判定・理由と、応答から抜き出した並び（`key_orders`）で、並びを抜き出した元の応答そのものは保存していない。
  - 比べる前に、元の採点で 1 件だけ応答を見ると、「理由が先」の指定なのに、4 基準のうち 3 つで verdict が先に並んでいた（[`results/order_probe.txt`](results/order_probe.txt)）。そこで、出力を JSON のテキストで返させる方式（`NativeOutput`）でも各 1 回採点した（[`results/order_native/`](results/order_native/)）。
- 結果：

  | | 理由が先（3 回） | 判定が先（3 回） |
  | --- | --- | --- |
  | 根拠 | 10/10、8/9、8/10 | 9/10、10/10、10/10 |
  | 分かりやすさ | 10/10、10/10、10/10 | 10/10、9/10、9/10 |
  | 範囲・ヒント | すべて 10/10 | すべて 10/10 |
  | 回の表示（コード） | すべて 8/10 | すべて 8/10 |
  | 総合 | 8/10、7/9、8/10 | 8/10、8/10、8/10 |
  | 要確認 | 0、1、0 件（#06 の根拠） | 0、0、0 件 |
  | 応答で指定どおりの順に並んでいた項目 | 16、23、24 / 40（計 63/120） | 20、22、18 / 40（計 60/120） |

  - 一致率と要確認の件数の差は、同じ条件の中での回ごとのばらつき（例：理由が先の根拠 10/10〜8/10）と同じくらいで、順序による差とは言えなかった。
  - 通常の採点（出力をツール呼び出しの形で受け取る）では、応答の中の reason と verdict の並びは、どちらの指定でもほぼ半々だった。
    JSON のテキストで返させると、どちらの指定でも 40/40 がその順に並んだので、テキストで書かせればモデルは順序の指定に従える。
    ツール呼び出しの形では、返ってくる引数の並びと、モデルが書いた順との対応を確認できなかった。モデルが指定に従わなかったのか、API が並べ替えて返しているのかは、今回の実験では区別できない。
- 気づき・疑問：
  - 講義の LLM 採点の対処に「理由を先に書かせる」があるが、今の採点の仕組み（ツール呼び出しの形の構造化出力）では、本当に理由が先に書かれたかを応答から確かめられなかった。順序を効かせたい、または確かめたいなら、JSON のテキストで返させる方式にして、並びを記録するのがよいと思う。
  - 今回の 10 件では、どちらの順序でも一致率はほぼ同じだった。もともと一致率が高く、自分が不合格にした項目も少ないので、順序の効果が出にくい評価セットだった可能性がある。判断が割れやすい項目（#06・#08 のような）を増やして試したい。
  - temperature 0 でも、同じ条件で判定が回によって変わった。基準や設定を 1 つ変えて比べるときは、1 回ずつではなく複数回採点して、ばらつきと比べる必要がある。
  - 限界：各条件 3 回（JSON のテキストは 1 回）、10 件、1 つのモデルだけ。並びを確かめるなら、次は元の応答（引数や JSON テキスト）も保存したい。
